# Mac 配信のメモリ保護（2026-10-02 更新）

今回のMacでは保存設定 MEMORY_GUARD=1 を有効化。
OSのメモリ圧力を5秒ごとに読み取り、開始前と試聴・終了音声準備後にも検査する。
`memory_pressure -Q` の割合はOSのメモリ圧力由来の指標であり、物理RAMの単純な空き率ではない。

- 開始には圧力normalかつ指標25%以上が必要。不明時も開始しない。
- warningまたは20%以下ではStudioの重複プレビューと任意の画面計測を休止。
- critical、10%以下、または警告/計測不能が30秒続く場合はゲーム制御を止め、事前生成済みの終了音声で終了を試みる。20秒以内に終わらなければ番組と所有OBS出力を停止。
- 5%以下では挨拶を待たず停止。次の配信を自動再開しない。
- Studioプレビューは初期休止。OBSの配信映像はそのまま。
- ゲーム画面の追加計測は標準OFF。必要時のみ GAME_FRAME_PROBE=1 で監視プロセスを起動。OBS統計の監視は継続。
- npm start / ランチャーは別プロセスの監督付き。StudioのV8ヒープ上限1024MiB、解析サイドカー256MiB（プロセス総メモリの上限ではない）。
- npm testは並列実行せず順番に実行する。配信中にテスト一式、ビルド、動画編集や追加モデルの起動は行わない。

検証: 模擬圧力による開始拒否、30秒継続、回復、危険時終了通知、5%以下への緊急移行、計測失敗、二重計測防止をテスト。実際にメモリを枯渇させる試験は行わない。他アプリの急増やOS強制終了を完全に防ぐ保証はない。

## 別のMacへ現在の設定を導入する

`config/ollama-low-memory.plist` は、公式Ollamaが `/Applications/Ollama.app` にあるMac用のユーザーLaunchAgentひな形。秘密情報は含まない。配信と他のOllama利用を止め、既存Ollamaアプリ/サーバーを終了したあと、以下で導入する。すでに同名サービスがある場合は内容を確認し、上書きや二重起動をしない。

## 2026-10-02 の品質を維持する対策

01:25開始の配信は、01:39:40からOSのwarningが続き、30秒後に保護終了が要求された。01:40:15に停止。停止条件を緩めず、使われていないリソースを解放する。別作業のVMや共有Ollama利用もあるため、単一のプロセスだけを原因とは断定しない。

- 会話は `qwen3.5:9b`、コンテキスト4096、ノアは同じコハクの声。映像の解像度・30fps・ビットレートをこの対策で下げない。
- OBSの専用Stageは、表示されていないときにブラウザを終了する。準備処理では全出力の停止を検査し、既知の専用ソース名・同一オリジンのStage URL・レイヤー・トークンを照合する。別のソースは変更しない。非表示の旧Stageを解放する前にも `GetSourceActive` の両フラグを確認する。再表示後は描画・音声のleaseと再生実績を改めて確認する。
- Studio試聴用Blobは次の音声への置換または試聴画面を閉じたときに解放する。再生中・再試聴用の現行音声は保持する。音声の順序制御Promiseに完了済みPCMを残さない。
- AivisSpeech 1.0.0は複数の声のモデルを同時保持する。このMacでは起動時に未使用のまおが先に読み込まれ、その後コハクが追加されていた。配信停止中に設定を非公開バックアップし、`userCharacterOrder` の先頭を既存のコハクにして正常再起動。モデルは削除していない。同じコハクの音声生成後、engineのphysical footprintは約3.6GiBから約1.5GiBへ減少。生成音声は確率的であり、波形の完全一致を意味しない。
- LaunchAgentひな形を実機の `LLAMA_ARG_CACHE_RAM=0`、`LLAMA_ARG_CTX_CHECKPOINTS=2` に合わせた。モデルの重み・量子化・声は変えない。共有Ollamaを利用中の別作業を、設定反映のために勝手に停止しない。

別の実験として、元9Bモデルから未使用の画像認識tensorだけを除く候補をGit外に作成した。言語442 tensor・残存40 metadataは全件一致を確認し、約871MiBの画像用重みを除去。元モデルは保持。候補を登録できたことと本番の会話品質・長時間安定性の確認は別であり、本番設定は自動で置き換えない。モデル変更時の試聴確認も省略しない。

短いテストで正常でも3時間の安定性は未証明。次の検証では実際に使うOBS・ゲーム・同じ声・会話モデルで継続測定し、OS圧力、プロセスphysical footprint、OBSの描画/エンコード遅延と音声再生実績を記録する。他作業が共有モデルを追加ロードした場合も識別できるようにする。

## KEEP_LIVE=1（配信を止めない運用・任意）

- 警告/計測不能が30秒続いただけでは停止しない（`sustained_warning` は警告として表示のみ）。
- **critical・10%以下・5%以下でも配信は止めない（2026-10-04〜）。** 代わりに「話の一時停止（メモリ保留）」に入る。
  - 放送中の一言は最後まで流し、次の一言は作らない・始めない。コメントへの返事の準備も止める（コメントの受け付けは続く）。ゲームは一時停止。
  - ローカルの会話モデル（Ollama）を解放する（`keep_alive: 0`。9Bで約6GB）。クラウドの会話モデルなら解放するものはない。
  - OBSの配信・録画、声のエンジン、ステージはそのまま。何も強制終了しない。
  - 圧力normalかつ指標25%以上（配信を始めるときと同じ基準）が20秒続いたら自動で再開する。再開後10分以内にまた保留になった場合は、次の再開に必要な時間を倍にする（最大5分）。モデルの再読み込みで保留と再開を繰り返さないため。
  - 監査ログに `memory_hold` / `memory_release` / `memory_resume` を残す。
  - 審査を通らない発話を流さない点、モデル・声・試聴の条件は変わらない（同じモデルの再読み込みは試聴のやり直しを要しない）。
- 限界：OS 自体が他のプロセス（OBS など）を強制終了するほどメモリが尽きた場合は防げない。保留中に回復しないときは、配信者が他のアプリを閉じる・会話モデルを小さくするなどの対応が必要。
- 生成・音声の失敗が4回続いても番組を止めず、間隔を空けて再試行を続ける。審査を通らない発話は流さない。
- 審査を通らない内容は飛ばして進み、3回続いたら15秒待つ。締めの挨拶が通らない場合だけは従来どおり終了する。
- 既定はOFF。OFFのときの動作は上の一覧のまま。
