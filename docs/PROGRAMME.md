# rc.5：同じ宣言を繰り返す配信から、結末のある企画雑談へ

## 採用する番組の仮説

ノアの「それ、本当に便利？」会議。身近な制約のもとで案を出し、困る点を発見し、考え直す。ゲーム、専門知識の講義、最新ニュース、架空の視聴者参加には依存しない。

これは視聴回数を保証する方式でも、成功済みチャンネルの数値を移植したものでもない。現時点では、番組仮説と、それを試す制御を実装した段階。最初の視聴者を「AI技術に詳しい人」だけに限定せず、タイトルのお題に自分の意見を持てる人を入口として想定する。

## 調査で確認した事実と、この実装の判断

YouTube公式は、視聴者との関連性や満足度、適切な長さ、内容に合ったタイトルを説明している。[1] 冒頭30秒の維持率の説明では、タイトル・サムネイルの期待と冒頭内容の一致を挙げる。[2] したがって、名乗りを繰り返すより最初から具体的な問題へ入る方針にした。15分がアルゴリズム上優遇されるという主張ではない。

縦型ライブには、モバイルのShorts等から発見される導線がある。[3] そのため任意の縦型表示を用意したが、表示回数の保証やYouTube側の同時送出設定は行わない。Shorts切り抜きは、単独で内容が分かる場面を選ぶという公式の案内に沿い、元の番組と内容を一致させる。[4]

反復的・量産的な内容の収益化と、おすすめ表示は別問題。AIを使用しただけで収益化不可とはしない一方、毎回同じ展開・結論を言い換えて量産する運用は避ける。[6]

## 選択できる3つの企画

| ID | タイトル案 | 3つの検討 |
|---|---|---|
| room | 家具は3つだけ。机・椅子・ベッドで本当に暮らせる？ | 服の収納 → 食事・仕事・来客 → 便利さと居心地 |
| holiday | 何もしない休日に、予定を入れたら負け？ | 空白の予定表 → 楽しみの詰めすぎ → 休み終わりに残るもの |
| robot | 家事ロボットに一つだけ頼むなら、何を任せる？ | 洗濯の終わり → 掃除と片付け → 任せられる範囲 |

各企画は3幕、各幕は9つの異なる課題。27段階を話し終えると締める。新規設定では15分が上限であり、15分ぶん話し続ける保証ではない。実音声の長さ・コメントの量で所要時間は変わる。既に保存している30分等の設定を勝手に書き換えないが、話し切った後に時間を埋めるループは行わない。

最初の公開候補はroom。タイトルの「本当に暮らせる？」を、衣食住の具体例で検討できる。画面に何を考えているかが残り、途中参加でも分かる構成を狙う。

## 初回の展開例

最初から「完璧に完成」と宣言しない。

1. 短い名乗りと問い：「家具を三つに絞った部屋で、まず服をどこに置くか考えてみよう」
2. 具体的な穴：「机と椅子とベッドを選んだけれど、服の置き場所がないね」
3. 問題を映像として想像できる例：「洗った服を床に置くと、小さな障害物が増えそう」
4. 別の案：「椅子を収納箱に変えてみる？」
5. トレードオフ：「物は片付くけれど、長く座れるかな？」
6. 比較と暫定結論。その後は、同じ机で食事する場面へ。

上は今回作った台本例で、実モデルが実際に話した記録ではない。APIなしデモの台詞は`config/programmes.json`に含む。本番モデルには台詞例を渡さず、現在の課題・実際の発言・コメントだけを文脈として渡す。

## コメント0件とコメントあり

コメントがなくても現在の課題を進める。コメント募集は必須にしない。各幕1回だけ問いかけを許す候補を持ち、直近に質問をした場合は3分間募集しない（初期方針であり最適値の証明ではない）。モデルが必ず守るという保証ではない。

採用・引用可のコメントは既存のVOICEVOXで読み上げ、その間に回答を準備する。コメント自体をノアが考えた意見として記憶しない。読み上げ終了と回答準備完了の両方を待つ。ホスト音声は設定したVOICEVOX/Supertonicを維持。コメントを読んだことを理由にモデルが実音声を聞いたと説明しない。

視聴者がいない、コメントがない、投票がないことを隠して、架空の賛成や投稿者を作らない。参考例は「自分に条件を足す」「番組で用意した問い」として扱う。

## 企画の編集（Studio から）

`config/programmes.json` が組み込みの企画。Studio の設定ページ「企画の編集」で保存した企画は `data/programmes/<id>.json` に丸ごと保存され、起動時に同じ id の組み込みと置き換わる（`src/programmes.mjs` の `loadProgrammes`）。保存前に `validateProgramme` が、テストが組み込みに課すのと同じ上限（見本 2 文・180 文字、課題の重複なし、段階数・ゲーム指定の固定、制御文字なし）を検査し、通らないものは保存しない。編集できるのは言葉（企画名・問い・狙い・挨拶・各段階のラベル・課題・見本・画面表示）だけで、`lobby` / `game` / `invite` などの進行フラグは組み込みのまま。

## ゲーム企画 NOA BLOCKS（`noa-blocks`）

「ノアの夜ふかしゲーム部」。落ち物パズル（Blockrain.js 0.2.1を無改変で同梱し、`public/noa-blocks.mjs`で拡張）をノアが実際の入力（回転・左右移動・ソフトドロップ）で遊び、雑談しながら自己ベストを目指す。名称はNOA BLOCKSで、Tetrisとは名乗らない。

- **実行者は1つ**：ゲームを動かすのは音声リースを持つStage（OBSソース）だけ。結果は`POST /api/renderer/game`（リース検証・`sanitizeGameReport`で項目と数値範囲を制限）でサーバーへ送る。他の視聴ページは受け取った盤面を表示するだけ。
- **ラウンド進行**（`src/blocks-show.mjs`）：紹介6秒 → 3分プレイ → 結果12秒 → 次の準備8秒。既定6ラウンド。自己ベストは速度別に`data/noa-blocks-records.json`へ保存し、結果発表はその記録との比較だけを言う。
- **次の速度**：コメントに「ゆっくり／標準／速め」があれば次ラウンドに適用し、実際に適用した速度だけを返答する。
- **イベント方針**：2ライン以上の消去・危険（14段以上、10段以下で解除）・持ち直し・ゲームオーバーは短い定型台詞。1ライン消去は表情だけ。表情は台詞より先に即時。台詞は優先度順・古い下位イベントは統合し、放送直前に「まだ正しいか」（有効期限、危険は現在の高さ）を再確認して外れたら話さない。プレイ中は直前の発話から7秒は雑談を入れない。
- **Jev**：ゲームの定型台詞も他と同じく`Jev.speech()`を通る（`game_reaction`／`game_fact`）。ゲーム名や遊び方の質問にはモデル生成ではなく、アダプタが持つ事実から作った文で答える。
- **画面**：スコア・ライン・時間・NEXT・最近のイベントはすべて実データ。視聴者数や架空のコメントは表示しない。

## ゲーム企画 Vampire Survivors（`noa-vampire`）

「ノアの夜ふかしゲーム部」のVampire Survivors版。ゲームのプラグイン `games/vampire-survivors/`（追加・差し替えの方法は `docs/GAMES.md`）。ゲームはスタジオの外で動き、操作はJev（別リポジトリ jev-vampire-survivors の `tools/auto_session.py`：起動・メニュー・プレイ・レベルアップ・ゲームオーバー後の再起動まで自動）。ノアは操作しているプレイヤーとして一人称で実況する。概要欄などでは「AIが操作・実況」と明記する。

- **状態の受け取り**（`src/run-log-feed.mjs`）：ブリッジは同時に1クライアント（操作側）だけなので、スタジオは接続しない。操作側が1手ごとに書く `<GAME_LOG_DIR>/<run>/decisions.jsonl`（旧名 `VAMPIRE_RUNS_DIR` も有効） を読むだけ（`auto_session.py` の既定では jev-vampire-survivors の `runs/`。ゲーム内録画 `--record` はネイティブ解像度のPNG保存でゲームが止まるため、映像はOBSのウィンドウキャプチャで取る）。起動後に書かれたログだけを対象にし、新しい run のディレクトリが現れたら次のラウンドとして扱う。
- **ラウンド進行**（`src/vampire-show.mjs`。雑談→前置き→ゲーム→結果の流れは共通の `src/external-game-show.mjs`）：1回のプレイ＝1ラウンド。開始（自己ベストの案内）→ プレイ → ゲームオーバーなら結果（生存時間・到達レベル・自己ベストとの比較）→ 観測に基づく振り返りと次回の方針 → 休憩 → 再開の挨拶。ゲームオーバー受信から約60秒を目標にし、振り返りと挨拶の音声完了を確認して次へ進む。詳しくは[振り返りと再開](ROUND_REVIEW.md)。自己ベストはキャラクター別に`data/vampire-records.json`。時間切れで止まったプレイは記録にしない。番組はセッション時間で締める。
- **イベント方針**：新しい武器・宝箱・体力低下（35%未満、60%以上で解除）・持ち直し・敵の急増（40/80/150/250体）・ゲームオーバーは短い定型台詞、レベルアップは優先度低め。数字や武器名はすべて観測値（武器名はゲームの選択肢に表示された日本語名）。放送直前にまだ正しいか（有効期限、体力低下は現在の体力、レベル・武器数が変わったら数字を含む台詞は捨てる）を確認する。
- **Jev**：NOA BLOCKSと同じく、定型台詞も`Jev.speech()`（`game_reaction`／`game_fact`）を通る。モデルが言ってよいのは observation の値（経過時間・レベル・体力・敵の数・武器・自己ベスト）だけ。
- **画面**：OBSでゲームのウィンドウをキャプチャし、その上にStageを`#layout=overlay`（背景透過、ノア右下・字幕左下・回数と自己ベスト）で重ねる。

## ゲーム企画 スマブラSP 観戦（`noa-smash`）

「ノアの夜ふかしゲーム部」のスマブラSP版。ゲームのプラグインは `games/smash-ultimate/`（`player: "operator"`、`capture.kind: "switch"`。仕組みは `docs/GAMES.md`）。**配信者が Nintendo Switch で遊び、ノアは隣で見ている実況役**として話す。操作役プログラム・画面認識はなく（`docs/SMASH_KIRBY_RECOVERY.md` の復帰制御は接続していない）、ノアが知っている試合の事実は Studio で押された報告だけ。

- **準備**：Switch接続（`/switch`）で機器を選び、プレビューとテスト録画で映像・音を確認する。設定（`/setup`「ゲーム配信」）でゲーム音のオン／オフと大きさを決める。番組を準備すると `Jev Studio - スマブラSP` シーンに Stage（`#layout=game`）と Switch の映像（と音）が入る。
- **進行**：雑談（既定5分、`show.lobbyMinutes`）→「ゲームを始める」→ 前置き → 開始の告知 → 試合。Studio の「試合の報告」（試合開始・撃墜した・撃墜された・勝った・負けた）を押すと、ノアがその出来事を定型台詞（各2文まで、`Jev.speech()` の `game_reaction`）で実況する。勝敗で結果（`resultsMs`）→ 次の「試合開始」。
- **数字**：撃墜数・被撃墜・今日の勝敗は報告の集計だけ。「何勝？」には集計から答え（`game_fact`）、通算は `data/smash-records.json`。報告されていないことは言わない。
- **画面**：ゲーム枠に Switch の映像、ラベルは「AIが実況中」。回数表示は試合数。
- **審査**：定型台詞 13 本は 2026-10-03 に本物の Jev で全件通過を確認した。「撃墜」や「2機目」「1勝目」のような数え上げは `safe`／`honest` が下がって落ちたため、出来事を穏やかに言う台詞に差し替え、数字は「何勝？」への `game_fact` の答えに任せる。台詞を変えたら同じ審査をやり直す（閾値は変えない）。

## 画面

横型は1920×1080。企画タイトル、現在の幕、いまの問い、完了した段階、字幕を表示する。未完了の課題は「次に考えること」と表示。小さい内部ログやモデルの確率値を放送の主役にしない。課題の進行は視聴者の投票結果ではない。

任意の縦型は1080×1920。既存Stage URLの`#token=...`の後ろに`&layout=vertical`を追加し、OBSブラウザソースの幅1080・高さ1920、送出キャンバスも対応させる。`#`を追加し直したりトークンを公開したりしない。YouTubeへ縦型として送る設定はOBS/YouTube側で確認する。横型映像を無検証で中央クロップするより、文字と顔を別配置するための表示モードである。

これは追加のOBSシーン自動生成・デュアル配信機能ではない。rc.3の遠隔開始は標準の専用OBSソースを検証するため、別の縦型シーンへ変更して自動開始できるとは保証しない。最初は標準横型＋録画を使い、縦型は別途ローカル試聴する。2つのページで音声所有権を奪い合わないよう、再生するソースは1つだけにする。

## 発見される入口と最初の試験

まず3企画を各1回試し、同じ声・同程度の条件で比較する。次の3回は、良かった企画の条件や問いを実質的に変える。同じ台本を6回配信する提案ではない。人数が少なければ統計的な優劣を断定しない。

1回から良かった20〜45秒程度を1本選ぶ案。尺は実測最適値ではない。「自分の案→困る点→考え直す」の一往復だけでも伝わる区間を選ぶ。面白い場面がなければ切り抜きを量産しない。切り抜き候補の記録は、その場面が面白かったという自動評価ではない。

`npm run episode:brief -- room`でタイトル、サムネイル文字、説明文の初期案をJSON表示する。YouTubeの動画やタイトルを作成・変更しない。音声のクレジットは実際の使用話者で追記する。

ライブの平均視聴時間、総再生時間、平均同時視聴者、新規登録者をYouTube Studioで確認する。[5] 冒頭や離脱箇所のハイライトはデータ条件があり、少数再生で常に表示されるわけではない。[2] コメント数0だけで失敗とは判断しない。

今回、管理画面に「進行記録を保存」を追加。各発話がローカルで終了通知された時刻と課題IDを保存できる。録画を見返す際の補助であり、YouTubeの維持率データ・視聴者が実際に聞いた秒数とは別。本文・コメント・キーはレポートに含めない。録画と照合してから切り抜き位置を決める。
