# カービィ専用・復帰制御（2026-10-01）

## 結論と現在地

対象は **スマブラSPのカービィ1体**。多キャラ対応は追加しない。
目的は「ジャンプできる」ではなく、**復帰阻止を回避し、必要なら反撃し、その行動の硬直後も戻れること**。

これは復帰計画器・入力ガード・Jev接続部・実機計測用インターフェースの実装であり、完成した自動プレイヤーではない。実機勝率・復帰率・映像認識精度は未測定。Switch/Piへの導入、ペアリング、操作、公開配信、課金はこの変更では行っていない。既存のVampire配信・OBS・音声ゲートには接続しない。

既存の `docs/SWITCH_MINECRAFT.md` が述べる通り、現在のSwitch対応は読み取り診断と手動配信準備までである。自動認識器や操作APIが既にある前提では実装しない。

## 重要な判断

### 「回避できる」と「回避後に生き残る」を別々に判定する

Ultimate Frame Dataのカービィ資料では、空中後攻撃は全体40F、空中N攻撃は52F、通常空中回避は62F、横方向空中回避は102F。空中回避の無敵区間は全動作時間ではない。

これらを単なる待機タイマーだけに使うのではなく、**技の全硬直を含む計測軌道**を用意する。短い無敵区間だけを切り出した回避、攻撃発生だけを使った反撃を認めない。着地・崖つかまりで合法的に早く終了する場合は、計測された各フレームの `canLand` / `canGrabLedge` と、ステージの受け入れ領域を使う。

反撃のヒットを仮定して敵の攻撃範囲を消さない。相打ちや空振りも考え、敵の攻撃を残したまま復帰の続きが成り立つ候補に限定する。相手の技を中断させた事実は次の映像観測から反映する。

### 生存の優先順位

1. 撃墜ライン・ステージ衝突を避け、崖または着地地点までつながる経路を残す。
2. 時間付きの敵攻撃範囲を、移動・ジャンプ・計測済みの回避で避ける。
3. 全硬直後にも復帰が成立するときだけ反撃候補を許す。
4. 崖をつかんだだけで成功としない。崖上がり後、地上で操作可能な状態が30ゲームフレーム続くことを初期の復帰成功条件にする。

`no_model_safe_route` は「この限定探索では妨害を避ける経路が見つからない」であり、「物理的に復帰不能」とは限らない。妨害を受けるが目標まで届く候補は `emergency` に別表示する。未検証の緊急候補を自動で実機へ送らない。このため難しい局面で見送る可能性があり、上級者水準の制御はまだ主張しない。

### キャラと環境を固定

`character=kirby` 以外は拒否。ステージ、ゲーム版、コントローラー設定、計測IDが変われば計測を無効にする。初期の実機評価は1対1・アイテムなし・ギミックなし・同一ステージ。コピー能力・ストーン・場外への追撃は復帰用候補に入れない。

空中ジャンプ残数は `[確実に残る数, 残っている可能性のある数]`。ボタン送信時に下限を予約消費し、ジャンプが実際に出た固有イベントで上限を消費する。被弾・崖つかまり・再接続で自動補充しない。確認済みの接地で補充する。崖で回復する資源が別途確認できても、この初期版は過大評価しない保守的な扱いにする。

## 軌道ライブラリを実機で作る

**テスト用データをそのまま実機に使わない。** `test/smash-kirby-fixtures.mjs` の座標・速度・時間軌道は人工データで、カービィの運動を再現しない。

現時点で映像から実機の状態を作る認識器と、学習済み重みは存在しない。この変更が受け取るのは構造化済みの観測。以下は必要な収集作業であり、完了済みではない。

- UGREENの実際の取り込みfps・映像の古さ・フレーム欠落を測る。広告上の入力fpsをUSB出力fpsと同一視しない。可能なら60fpsを確認し、30fpsしか取れなければ観測誤差と見逃しを広げて評価する。
- ステージの移動・ズームを除去し、カメラの画素座標でなくステージ基準の座標にする。左右の崖、足場の壁・下面、撃墜ラインの内側に置く安全境界を計測する。境界を画面端で代用しない。
- カービィと相手を個別追跡し、位置・速度・向き・被弾/硬直/操作可能/崖つかまりを継続して推定する。見えていない資源を満タン扱いしない。
- 各空中ジャンプ段数、開始速度・高さ、左右、入力遅延ごとに、押下から技終了までを繰り返し収録する。ジャンプ、内外移動、空中回避、空後/空上等、上必殺、崖上がりを個別に記録する。上必殺は上昇だけでなく下降と崖をつかめる区間を含める。
- 同じ条件での位置の最小/最大をフレームごとの軌道包絡にする。入力待ちとキャプチャ遅延による移動も含める。独立した試行で軌道が包絡を外れないか確認し、計測不足の開始条件へ外挿しない。
- 攻撃の判定位置・発生/持続/後隙と相手の移動候補を時間付きの範囲にする。単に `相手が近い` では不十分。敵が動かない軌道だけを予測すると復帰阻止に弱い。

軌道例の完全なスキーマはfixture参照。実機ライブラリは `source: measured` とし、記録動画、入力ログ、ゲーム版、設定、撮影経路、誤差検証の証跡を別途保存する。`approval.hardwareVerified` と `approval.evidence` はオペレーターによる承認記録であり、証明書でも暗号学的な検証でもない。単にフラグを書き換えて実機検証済みにしない。

`maxObservationAgeMs` / `maxInputP95Ms` はその軌道包絡が実際に検証された遅延条件。未知の遅延やカメラ設定の変更を同じ包絡に流さない。計測誤差が大きいほど使える経路は減るが、安全性を装うために数値を狭くしない。

## 観測インターフェース

- `self.x/y`: カービィの保守的な占有範囲。`vx/vy`: 速度区間。座標はy上向き、ステージ幅で正規化。
- `self.actionable`: 今その入力を開始できるという観測。被弾中にAPI応答が返ってもキャンセル可能とはみなさない。
- `threats.boxes`: 観測フレームから `from..to` の間に相手の攻撃が占有し得る矩形。移動する攻撃は時間ごとに複数の範囲を入れる。
- `threats.coverageFrames`: 妨害を予測した長さ。空配列でも信頼度や予測期間が不明なら安全扱いにしない。
- `stage.targets`: 計測された崖のつかまり領域/着地領域。`solids` は壁・ステージ下面。目標へ向かう途中の衝突も検査する。
- 各motion sampleの正のdxはステージ方向。右側では反転。vxと向きの開始条件も同じ座標で評価。
- `decisionAtMs`: オフライン再生時の判断時刻。観測時刻との差を保持して、通信遅延をなかったことにしない。

軌道包絡の独立な矩形近似、限られた探索深さ、敵の予測誤差が残る。これはゲームエンジンの完全シミュレーターでも、厳密な生存確率計算でもない。

## Jevと操作の接続

既存 `Jev.ask` を注入することで、利用上限・課金計測・応答検証を再利用する。

```js
const advisor = new JevRecoveryAdvisor({
  ask: (state, questions, signal) => jev.ask(state, questions, signal),
});
// 低頻度の別タスクでrequestを呼ぶ。60Hzの操作ループではawaitしない。
const advice = await advisor.request(observation, locallyCheckedPlan);
// 実行直前に現在の候補へ再照合する。Jevは任意のボタンを発行できない。
```

`confidence` は復帰成功率ではない。反撃を一度選んだだけで優れているとは判定しない。Jev有無を同じ認識器・操作器・試行条件で比較する。

`KirbyInputExecutor` は既定dry-run。実機入力は明示的な `live: true` と `arm()`、検証済みライブラリ、継続した観測が必要。`send(packet)` は既存の持続パイプへ書くコールバックとする。ボタンごとにSSHを起動しない。`startedSkill.inputId` を `KirbyResources.reserve` と結び、画像認識の技発生イベントを `observe` に渡す接続が必要。これらの認識器・セッション統合は未完了。

フレーム重複・順序逆転・時刻の逆行・観測の失効・ストック変更時は入力を解放して再有効化を必要とする。既に開始したゲーム内の技そのものを任意に取り消せるわけではない。入力を止めることが復帰の最善策とは限らず、実機運用前に最終手段の制御を校正する必要がある。

## Piブリッジ

ブリッジはホスト名やSSH鍵を収集せず、stdinからのみ受け取る。公開HTTP/UDPサーバーは作らない。Mac→Piは同期した時計と保護された持続接続が前提。パケットにはsession・単調増加seq・絶対失効時刻を入れ、古い入力の有効期限を到着時に延長しない。時計ずれは拒否する。Node側が停止するとPiのwatchdogがニュートラルに戻す。

```sh
# これは入力の検証のみ。NXBT不要、ペアリングなし。
python3 scripts/smash-kirby-nxbt.py --dry-run
# 以下は実機を操作する明示モード。配信や別ゲーム操作を止め、Piでのみ実施。
# python3 scripts/smash-kirby-nxbt.py --live
```

120HzはNXBTへの投入目標であり、Switchでの1フレーム精度やACKを保証しない。実際の押下/解放成功率は録画で別途評価する。認識器がなくstdinへ適切な状態が流れない現在、このブリッジだけでスマブラを自動プレイできるわけではない。

追加JavaScriptテスト40件、Pythonテスト8件を作業環境で実行。全リポジトリの `npm run release:check` はこの切り出し環境では未実行。既存GitHub CIはpush/PRで全体の構文チェック・Nodeテスト・パッケージ検証を実行するため、その結果を別途確認する。

## 「使いこなした」と判断するための合格基準案（未達）

固定キャラ・固定ステージで、左右、吹っ飛び角度、高低差、残ジャンプ0..5、回避済/未使用、ダメージ帯を分ける。復帰可能と人/実測で確認したケースだけを分母にする。調整に使わなかった開始条件・録画で評価する。

- 操作：ジャンプ・各空中技・上必殺・崖上がりの実入力成功率99%以上を目標。取得fpsと入力遅延のp50/p95/p99も併記。
- 無妨害の復帰：1,000試行以上、成功率99%以上を初期目標にする。平均だけでなく条件別の失敗と95%信頼区間を出す。
- 妨害付き復帰：固定された弱い相手だけでなく、空中追撃・飛び道具・崖待ち等の未使用パターンで評価。人操作または調整前の制御より改善したかを比較する。
- 反撃：命中率だけでなく、反撃後の復帰率、自滅率、相打ち、ジャンプ消費を評価。ダメージを増やして生存率を下げる変更は採用しない。
- 崖：つかまりで終えず、崖上がりの選択と地上での操作可能状態まで追う。

カービィを「完璧」と言うには、復帰以外の間合い、差し返し、コンボ、撃墜、着地、DI/SDI、受け身、崖の読み合い、相手キャラ別の反応も必要。この変更はそれらの完成を主張しない。最初の対象をカービィから広げず、実機データ・映像認識・セッション接続を埋めて評価を進める。
